# 5x5x5 engine

Part of [Engines and limits](_index.md). Numbers across all engines are on [Performance](../performance.md).

## What it solves and how

`FiveSolver` solves a 5x5x5 whose six face centres stay in place, as a port of [cube555](https://github.com/cs0x7f/cube555).

1. Five searches in a row bring the centres and then the wing edges into the state of a 3x3x3. Each is an iterative-deepening search guided by a pruning table and keeps several candidates for the next one (200, 500, 500, 500 and 1 for phases 1 to 5, as in the reference). Phase 1 searches from three conjugated copies of the cube; phase 2 hands three conjugated copies of each solution to phase 3.
   The answer reports the phases as stages: phases 1 and 2 as `centres staged`, phase 3 as `wings staged`, phases 4 and 5 as `centres and wings paired`, then `3x3 stage` (see [Move icons](../icons.md#phases)).
2. The corners, middle edges and centres form a 3x3x3 (stickers in rows and columns 0, 2 and 4). `FiveSolver` hands it to the 3x3x3 solver it was built with, through the `Solver` trait, and appends that solution. A turn that ends one part and begins the next on the same face is merged or cancelled.
3. It checks that the 3x3x3 answer uses only single-layer turns, then replays the whole solution on the 5x5x5.

## Input and orientation contract

The cube is 150 facelets with the six face centres in place. It turns the two outer layers of a face (`R`, `2R`) and two-layer turns (`Rw`), never the middle layer (`3R`), so the solved cube is the solved facelet string and no rotation is involved. A cube whose face centres have moved is not accepted.

## Options

| Option | Effect |
| --- | --- |
| Move limit | Bounds the whole solution. No default. Without a budget the 3x3x3 stage is limited to 10 s, so a tight limit ends as `Exhausted` instead of searching for minutes. |
| Time budget | Expiry fails with `BudgetExhausted`; the message says so when the tables were still being built. |
| `min_probes` | Passed to the 3x3x3 stage; default 500 (as for the 4x4x4), so the tail is shorter than the first solution found. |
| Threads | `CUBACLE_THREADS` or `with_threads(n)` (default all cores). The search merges results in a fixed order, so without a time budget the solution does not depend on the thread count. The server uses one thread per solve. |

## Tables

237 MB of pruning tables in 12 files, byte-identical to the Java ones, plus about 70 MB of move and symmetry tables. A parallel breadth-first search builds them on the first solve or in `prepare()` and saves them in the cache directory (`CUBACLE_CACHE_DIR`, else `$XDG_CACHE_HOME/cubacle`, else `~/.cache/cubacle`) with a checksum and a format version; a missing, damaged or foreign file is rebuilt. The tables are identical for any thread count.

Cold build 3.3 s on 12 threads and 18.3 s on one; warm load about 1.0 s (the cache is streamed, which avoids a second copy of the largest table). Peak memory warm 335 MB (12 threads) and 327 MB (1 thread): above the 300 MB aim. The tables are 237 MB, about 70 MB are move and symmetry tables (measured with `vmmap`), the rest is the process.

## Performance

Apple M2 Pro (12 cores), release build, 100 random cubes, every answer replayed; both solutions finished by our 3x3x3 solver; first benchmark, 2026-10-22, with `tools/bench/run.sh`. The Java column of this table is its first run; see below for the warm figure.

| Total moves, mean / median / p90 | 73.1 / 73 / 75 | 73.1 / 73 / 75 | 73.1 / 73 / 75 |
| Solve time, mean / median / p90 | 865 / 656 / 1776 ms | 92 / 77 / 187 ms | 444 / 404 / 723 ms |
| Table build, cold | about 50 s | 3.3 s | 18.3 s |
| Table load, warm | 1.8 s | about 1.0 s | about 1.0 s |
| Peak memory, warm | 0.76 GB | 335 MB | 327 MB |

After twist-flip pruning and the default of 500 probes for the 3x3x3 tail (1 thread, the first 100 cubes, 2026-10-22; another process was running on the machine, load 3 to 7): total moves 70.97 mean / 71 / 73 / 74 max (73.05 before), time 470 ms mean (455 ms before: the longer tail costs about 3 %). With `MAX_DEPTH2` 12 the figures are 70.99 and 495 ms (noisy). Per-axis normalisation of the answer ([move metric](../performance.md#move-metric)) then gives 69.95 (median 70, p90 72, max 73; 485 ms), and `--slices` the same. The thread columns above predate this.

Answers with 1, 4 and 12 threads were identical on 300 cubes. The common-method run (300 cubes at 1 and 12 threads, 100 cubes in between; idle machine) measured, against a **warm** Java reduction of 575.7 ms mean (median 511, p90 922, max 2321; Java also needs 1.70 s to read its tables and 657 MB):

| Threads | 1 | 2 | 4 | 8 | 12 |
| --- | --- | --- | --- | --- | --- |
| Mean time | 408.4 ms | 239.5 ms | 142.4 ms | 89.8 ms | 100.2 ms (87.6 on the 100-cube set) |
| Cores busy (utilisation) | 1.0 | 1.97 (99 %) | 3.84 (96 %) | 7.38 (92 %) | 9.24 (77 %) |

The speed-up over warm Java is 1.41x at one thread and 5.75x at 12. The 865 ms in the table above is the mean of the first benchmark with a cold-started Java process; it is kept for the record and is not the warm figure. Every phase stops scaling at about 8 threads and the CPU per cube grows from 408 to 927 ms at 12 threads, because of speculative work (nodes roughly double in phases 2, 4 and 5). The best throughput is 3 solves in flight with 4 threads each (14.5 solves per second, median latency 192 ms), 1.26x that of one 12-thread solve at a time. See [Performance](../performance.md).

## Comparison with the Java original

Reference: [cs0x7f/cube555](https://github.com/cs0x7f/cube555); licence mechanics are in [NOTICE.md](https://github.com/wstein/cubacle/blob/develop/NOTICE.md).

Ported: the five phases, the pruning tables and their move order, including a Java shift bug in the skip masks that is kept on purpose, because without it the answers differ from Java's. New: the parallel table build and search, the table cache, the 3x3x3 hand-off through the `Solver` trait, and validation.

| | Claimed (README) | Measured (Java 21, M2 Pro) | Rust |
| --- | --- | --- | --- |
| Reduction moves | 51 to 52 | 51.5 | identical |
| Solve time | 1 to 2 s | 865 ms mean (cold start), 576 ms (warm, remeasured) | 92 ms (12 threads), 444 ms (1 thread) in the first run; 100 / 408 ms in the later run |
| Tables on disk | about 240 MB | 237 MB, 12 files | 237 MB, byte-identical |
| Memory | at most 500 MB | 1.6 GB cold, 0.76 GB warm (657 MB in the later run) | 335 MB warm (306 to 319 MB in the later run) |

The Java solver answers only the reduction, so both columns end with our 3x3x3 solver.

## Limits and failure modes

- `InvalidInput` for a cube that is not a 5x5x5; `CentersOffFace` for one whose centers are not on their own faces (a middle-layer turn, `3R`, in a scramble).
- `BudgetExhausted` on a spent clock; `Exhausted` for a move limit the 3x3x3 stage cannot meet.
- If the cache cannot be written the solver warns and rebuilds next time.

## Reproduce

```sh
cargo build --release
target/release/cubacle solve --size 5 --scramble "R U 2R Fw' 2U" -v
tools/bench/run.sh /path/to/cube555 /tmp/bench 100
```

The first prints `preparing the 5x5x5 tables (cache directory ...)` and a short solution; the second needs Java 8 or newer, `make` and a checkout of the original. For the cold start empty the cache directory first; `CUBACLE_THREADS=1` gives the single-thread column.
