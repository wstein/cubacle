# 4x4x4 engine

Part of [Engines and limits](_index.md). Numbers across all engines are on [Performance](../performance.md).

## What it solves and how

`FourSolver` solves any 4x4x4 by reduction, as a port of Tsai's three-phase method in [TPR-4x4x4-Solver](https://github.com/cs0x7f/TPR-4x4x4-Solver).

1. Phase 1 brings the centres into a state where every colour pair sits on one axis. It enumerates up to 10,000 solutions and keeps the best 500 in the priority queue of the original (about 2 ms).
2. Phase 2 finishes the centres without breaking the pairing of the wings, until 100 results exist.
3. Phase 3 pairs the wings and solves the centres (the original's third and fourth steps in one).
4. The corners, wings and centres now form a 3x3x3. `FourSolver` hands it to the 3x3x3 solver it was built with, through the `Solver` trait, asking for at least 500 probes (`SolveOptions::min_probes`, counted, not timed; the original does the same).
5. The model's moves are mapped back to real moves, the rotation is appended, and the whole solution is replayed on the 4x4x4. A mismatch is `Failure::Internal`, never a wrong answer.

## Input and orientation contract

The cube is 96 facelets. A 4x4x4 has no fixed centres, so the cube counts as solved when every face shows one colour in the standard scheme (U white, R red, F green, D yellow, L orange, B blue in the default notation), and the answer ends with the whole-cube rotation that gets there. The rotation is written as wide turns: `Rw Lw'` is the rotation about the R axis, and at most four such turns bring any cube to the standard orientation (3.1 moves on average). Layer turns only: `R`, `Rw`, never a slice turn. The solution solves the cube exactly as `Facelets::apply` replays it.

## Options

| Option | Effect |
| --- | --- |
| Move limit | Bounds the whole solution including the rotation. No default. With a limit, the 3x3x3 stage is limited to 1 s whatever the budget, so a limit the tail cannot meet ends as `Exhausted` (REST: 422 `no_solution_within_limit`). |
| Time budget | Expiry fails with `BudgetExhausted`; the message says so when the tables were still being built. Without a budget the 3x3x3 stage is limited to 10 s. |
| `min_probes` | Default 500 for the 4x4x4. Without it the tail was 1.3 moves longer. |
| Threads | `CUBACLE_THREADS` or `with_threads(n)` (default all cores, at most 256). Phase 1 is sequential; phases 2 and 3 search several (candidate, first move) pairs at once and join the results in the order one thread would find them, so without a time budget the solution does not depend on the thread count. The server uses one thread per solve. |

## Tables

About 12.1 MB: centre moves and pruning tables and a 2-bit wing pruning table of 31 million states, plus the tables of the injected 3x3x3 solver. Built on first use or in `prepare()`; no cache file (the saving of a cache measured for the Java original was 0.36 s of 1.23 s, so the first version builds in memory). Measured build: 0.37 s on one thread, 0.19 s on 4 and 0.17 s on 12 (the 1000-cube run); about 0.2 s on 12 cores and 0.4 s on one in the CLI. Peak resident memory 65 MB (1 thread), 71 MB (4), 66 MB (12). The common-method run (200 to 1000 cubes, idle machine) measured 317 ms on one thread and 173 / 156 / 151 ms on 4 / 8 / 12 threads (2.0 / 3.0 / 3.8 cores busy), and peak RSS 62 to 64 MB; Java: init 0.80 s and 129 MB [M, [Performance](../performance.md#all-engines-in-one-table)].

## Performance

Apple M2 Pro (12 cores), release build, 1000 random cubes drawn by the original's generator (`Tools.randomCube(Random(1))`), every answer replayed; measured 2026-10-22 with `tools/bench/run_four.sh`.

| | TPR (Java), 1 thread | `FourSolver` 1 thread | 4 threads | 12 threads |
| --- | --- | --- | --- | --- |
| Moves without rotation, mean / median / p90 / max | 44.59 / 45 / 46 / 47 | 44.34 / 44 / 46 / 47 | same | same |
| Moves with rotation, mean / median / p90 / max | 47.71 / 48 / 50 / 51 | 47.47 / 48 / 49 / 51 | same | same |
| Time, mean / median / p90 | 115 / 99 / 197 ms | 72 / 62 / 117 ms | 40.0 / 37.8 / 56.8 ms | 39.5 / 38.1 / 53.4 ms |
| Table build | 0.8 s (3x3x3 included) | 0.37 s | 0.19 s | 0.17 s |
| Peak memory | not measured | 65 MB | 71 MB | 66 MB |

Answers with 1, 2, 4, 8 and 12 threads were identical on all 1000 cubes. Four threads cut the mean time to 0.56 of one thread (aim 0.5, missed): of the 73 ms average, phase 1 takes 2 ms and the 3x3x3 hand-off 21 ms, both on one thread, so four threads cannot go below 0.49 even if phases 2 and 3 (21 and 29 ms) scaled perfectly; they scale by about 2.9 on four threads. A second run with the instrumented common method (1000 cubes, idle machine) gave, per thread count, mean time and cores busy:

| Threads | 1 | 2 | 4 | 8 | 12 |
| --- | --- | --- | --- | --- | --- |
| Mean time | 72.2 ms | 52.1 ms | 41.7 ms | 40.6 ms | 41.6 ms |
| Cores busy (utilisation) | 1.0 | 1.53 (77 %) | 2.22 (56 %) | 3.60 (45 %) | 5.13 (43 %) |

At 12 threads the CPU per cube is 214 ms against 72 ms at one thread, and system time is 36 % of all CPU: the tasks are too fine and contend on one mutex. The 12-thread latency is 2.74x better than warm Java and the single-thread time 1.58x better; with one thread per solve and 12 solves in flight the throughput is 106 per second against 8.8 for Java (12.1x) and 4.4x that of sequential 12-thread solves. For latency use 4 threads; for many solves use one thread per solve. See [Performance](../performance.md#100-solutions-multithreaded-algorithm-or-single-core-solves-spread-over-cores) and the [planned optimisations](../performance.md#planned-optimisations).

## Comparison with the Java original

Reference: [cs0x7f/TPR-4x4x4-Solver](https://github.com/cs0x7f/TPR-4x4x4-Solver); licence mechanics are in [NOTICE.md](https://github.com/wstein/cubacle/blob/develop/NOTICE.md).

Ported: phases 1 to 3 (tables, move order, queues). New: the parallel phases 2 and 3, the hand-off to our 3x3x3 solver through the `Solver` trait, input validation, bounded loops (the reference has an unbounded `do..while` in phase 1; the port bounds it and returns `Exhausted`), and the final rotation as wide turns.

| | Claimed (README, 2011 laptop) | Measured (Java 21, M2 Pro) | Rust |
| --- | --- | --- | --- |
| Moves | 44.39 | 44.59 | 44.34 |
| Time per cube | 250 ms | 114 ms mean (115 in the first run) | 72 ms mean (1 thread), 41.6 ms (12 threads) |
| Start | 6 to 7 s | 0.8 s | 0.37 s |
| Memory | at most 30 MB | not measured | 65 MB peak resident |

The first three phases are identical to the original's on all 1000 cubes; the whole answer without the rotation is identical on 665, because the 3x3x3 tails come from different solvers.

## Limits and failure modes

- `InvalidInput`: not a 4x4x4, a colour scheme other than the standard one, a wrong number of stickers of a colour on the centres, a repeated or missing wing, or a corner twisted alone. Two swapped corners or wings are valid and are solved.
- `BudgetExhausted` on a spent clock (also while building tables); `Exhausted` for a move limit the tail cannot meet.
- It does not look for shorter answers than the original does.

## Reproduce

```sh
cargo build --release
target/release/cubacle solve --size 4 --scramble "R U Rw Fw' 2U" -v
CUBACLE_THREADS=1 target/release/cubacle solve --size 4 --scramble "R U Rw Fw' 2U" -v
tools/bench/run_four.sh /path/to/TPR-4x4x4-Solver /tmp/bench4 1000 1
```

The first two print the 6-move solution `U Uw' Fw Rw' U' R'` (the first solve prints `preparing the 4x4x4 tables`). The third needs Java 8 or newer and a checkout of the original; the 1000-cube figures above come from it.
