# 3x3x3 engine

Part of [Engines and limits](_index.md). Numbers across all engines are on [Performance](../performance.md).

## What it solves and how

`Min2PhaseSolver` solves any 3x3x3 with Kociemba's two-phase algorithm in the form of [min2phase](https://github.com/cs0x7f/min2phase). Phase 1 brings the cube into the subgroup generated by U, D, R2, F2, L2, B2 (corner twist, edge flip and the position of the four middle-layer edges solved); phase 2 solves the cube inside that subgroup. Pruning tables (move tables and distance tables over symmetry-reduced coordinates) guide both phases with iterative deepening. The search finds more phase 1 solutions than a plain two-phase search by trying the three axes, the inverse of the cube and pre-moves (moves applied before the scramble), as min2phase does. After the first solution it keeps searching for shorter ones until the move limit, the probe minimum or the time budget ends it.

The same solver is the last stage of the [4x4x4](4x4.md) and [5x5x5](5x5.md) engines, which hand it the reduced cube through the `Solver` trait.

## Input and orientation contract

The cube is 54 facelets. The centres are fixed, so the solved cube is the standard facelet string and the solution needs no final rotation. Colour input needs a scheme only when no centre colours fix it (see [Command-line guide](../cli.md#colour-schemes)). The command-line tool replays each 3x3x3 solution on the cube before printing it.

## Options

| Option | Effect |
| --- | --- |
| Move limit (`-m`, `max_moves`) | The longest solution to accept. Default 21; 20 or 21 is a good choice. A lower limit costs time (see Performance). |
| Time budget (`-b`, `budget_ms`) | Hard limit. A search with a budget is not deterministic. |
| `min_probes` | Keep searching until at least this many phase 2 probes were made, counted rather than timed, so shorter solutions come with a repeatable answer. Default none for the 3x3x3; the reduction engines ask for 500. |
| Threads | `solve` is one thread and deterministic. `solve_parallel` searches the six URF orientations of one cube on several threads. `solve_batch` solves many cubes on a process-wide pool whose size is read once from `CUBACLE_THREADS` (default all cores). |

## Tables

Built on first use or by `prepare()`; they belong to the solver instance and are shared by its clones, so create one solver and clone it (`Min2PhaseSolver::shared()` is a process-wide instance). There is no cache file. Measured cold build: 41 ms on one thread (20 ms before the twist-flip table) [M]; peak resident memory of a process that builds the tables and solves: 3.9 MB (2.8 MB before) [M]. The twist-flip pruning table is 4 bits per entry over 336 flip classes times 2187 twists, 367 KB, with 114 KB of move and conjugation tables beside it (the tables are not measured separately; Java: 68 MB, init 0.13 s).

### Shorter solutions: moves against probes and time

The first solution is not the shortest the search can find. `min_probes` (command line `--probes N`) and a minimum time (`--improve`) keep searching with a shrinking target, so every later solution is shorter than the one before. Measured on an Apple M2 Pro, 500 random cubes, move limit 21, tables prepared first, one run each (the machine carried a background load of about 2.5, so treat the times as approximate):

| Mode | Moves, mean | p90 | Time per cube, mean |
| --- | --- | --- | --- |
| default (first solution) | 20.83 | 21 | 0.8 ms |
| `--probes 100` | 19.87 | 21 | 4.0 ms |
| `--probes 1000` | 19.16 | 20 | 42.1 ms |
| `--probes 10000` | 18.59 | 19 | 466.2 ms |
| `--improve -b 10` | 19.56 | 21 | 10.0 ms (1 cube of 500 had no solution yet) |
| `--improve -b 100` | 18.99 | 20 | 100.0 ms |
| `--improve -b 1000` | 18.48 | 19 | 1000.0 ms |
| `--improve --parallel -b 100` | 19.67 | 21 | 101.6 ms |
| `--improve --parallel -b 1000` | 19.27 | 21 | 1000.0 ms |

`--probes` counts work, so a row is repeatable on any machine; its time column is only what this machine took. `--improve` spends exactly its budget and returns the best solution found by then; spending the budget after a solution exists is not an error. The `--parallel` rows are worse than the serial `--improve` rows with the same budget: in these runs, searching the six orientations at once did not find shorter solutions, so prefer plain `--improve`. Why is not investigated. Moves fall by 0.7 and then 0.6 per tenfold increase in probes (100 to 1000 to 10000). The 4x4x4 hand-off already asks for 500 probes.

Commands (the example prints one line per run):

```sh
cargo run --release --example improve_curve -- 500 default
cargo run --release --example improve_curve -- 500 probes 1000
cargo run --release --example improve_curve -- 500 improve 100
cargo run --release --example improve_curve -- 500 parallel 100
```

## Comparison with the Java original

Reference: [cs0x7f/min2phase](https://github.com/cs0x7f/min2phase) (Java), checked out at commit 4d183b9. The Rust core comes from the MIT-licensed [min2phase_rust](https://github.com/cs0x7f/min2phase_rust) of the same author; provenance is recorded in `NOTICE.md`.

What was ported: the two-phase search, the coordinate and symmetry tables, the three-axis, inverse and pre-move tricks. What is new in cubacle: the typed `Solver` interface and replay check, the persistent worker pool, `solve_batch` and `solve_parallel`, the probe minimum as a counted option, and the golden-file test that pins the search output for 554 fixed cubes.

Claimed by the Java project (`Benchmark.md`, not measured by us, machine not stated): full initialisation about 195 ms; 0.685 ms per cube for an unlimited search, 0.805 ms for 21 moves and 4.62 ms for 20 moves; memory about 1 MB per its table note; average length 19.29 with 500 probes taking 19.4 ms.

Measured by us (same 1000 cubes, same machine, warm JVM, one thread):

| | Java min2phase | cubacle |
| --- | --- | --- |
| Moves, mean / median / p90 / max | 20.52 / 21 / 21 / 21 | 20.81 / 21 / 21 / 21 |
| Time, mean / median / p90 | 0.567 / 0.349 / 1.165 ms (max 12.9) | 0.482 / 0.290 / 1.011 ms |
| Init | 0.13 s | 41 ms |
| Peak memory | 68 MB | 3.9 MB |
| Throughput, 12 solves in flight | | 6.5x Java single-thread [D] |

cubacle was 0.72x of Java on one thread while its core was an older min2phase variant without twist-flip pruning. It now has the upstream twist-flip pruning with conjugate pruning (a 4-bit table over flip classes and raw twists, and a second bound on the cube conjugated by a quarter turn about the U-D axis); the answers did not change (golden file and all fixtures pass untouched). Counted at the same place, cubacle searches 1,087 phase 1 nodes per cube against 4,710 before and 1,153 in Java, with 12.3 probes before the next change (7.4 in Java), and solves 1.75x faster than before. `MAX_DEPTH2` is now 12, as upstream (it was 13); that changes answers (golden file re-recorded, 225 of 554 rows) and on the 1000 cubes gives 1,159 nodes and 13.9 probes per cube, a mean of 20.67 moves (20.81 before) and 0.465 ms per solve (0.466 before) [M]. The Java claim above (0.685 ms) was measured on another machine and is not comparable with these figures.

## Limits and failure modes

- An impossible state (twisted corner, flipped edge, parity) or a facelet string that is not a cube is `InvalidInput`.
- A move limit the search cannot meet in the budget fails with `Exhausted`; a budget that ends first fails with `BudgetExhausted`.
- `solve_parallel` and time-budgeted searches are not guaranteed to return the same solution on every run; the result is always valid within the move limit.
- `solve_batch` ignores the time budget: every cube runs to completion.

## Reproduce

```sh
cargo build --release
target/release/cubacle solve --scramble "R U R' U'" -m 20 -v
RUSTFLAGS='-C target-cpu=native' cargo run --release --example benchmark -- 100
```

The first prints `elapsed ..., probes 1` and the solution. The benchmark is described in the repository README; the commands that produced the table above are on [Performance](../performance.md#reproduce).
