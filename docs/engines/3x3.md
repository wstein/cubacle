# 3x3x3 engine

Part of [Engines and limits](_index.md). Numbers across all engines are on [Performance](../performance.md).

## What it solves and how

`Min2PhaseSolver` solves any 3x3x3 with Kociemba's two-phase algorithm in the form of [min2phase](https://github.com/cs0x7f/min2phase). Phase 1 brings the cube into the subgroup generated by U, D, R2, F2, L2, B2 (corner twist, edge flip and the position of the four middle-layer edges solved); phase 2 solves the cube inside that subgroup. Pruning tables (move tables and distance tables over symmetry-reduced coordinates) guide both phases with iterative deepening. The search finds more phase 1 solutions than a plain two-phase search by trying the three axes, the inverse of the cube and pre-moves (moves applied before the scramble), as min2phase does. After the first solution it keeps searching for shorter ones until the move limit, the probe minimum or the time budget ends it.

The same solver is the last stage of the [4x4x4](4x4.md) and [5x5x5](5x5.md) engines, which hand it the reduced cube through the `Solver` trait.

## Input and orientation contract

The cube is 54 facelets. The centers are fixed, so the solved cube is the standard facelet string and the solution needs no final rotation. A cube whose centers a slice turn moved is renamed after its centers before it gets here (`cubacle::puzzle::oriented_by_centers`); the engine itself still answers `CentersOffFace` for it. Color input needs a scheme only when no center colors fix it (see [Command-line guide](../cli.md#color-schemes)). The command-line tool replays each 3x3x3 solution on the cube before printing it.

## Options

| Option | Effect |
| --- | --- |
| Move limit (`-m`, `max_moves`) | The longest solution to accept. Default 21; 20 or 21 is a good choice. A lower limit costs time (see Performance). |
| Time budget (`-b`, `budget_ms`) | Hard limit. A search with a budget is not deterministic. |
| `min_probes` | Keep searching until at least this many phase 2 probes were made, counted rather than timed, so shorter solutions come with a repeatable answer. Default none for the 3x3x3; the reduction engines ask for 500. |
| Threads | `solve` is one thread and deterministic. `solve_parallel` searches the six URF orientations of one cube on several threads. `solve_batch` solves many cubes on a process-wide pool whose size is read once from `CUBACLE_THREADS` (default all cores). |

## Tables

Built on first use or by `prepare()`; they belong to the solver instance and are shared by its clones, so create one solver and clone it (`Min2PhaseSolver::shared()` is a process-wide instance). There is no cache file. Measured cold build: 41 ms on one thread (20 ms before the twist-flip table) [M]; peak resident memory of a process that builds the tables and solves: 3.9 MB (2.8 MB before) [M]. The twist-flip pruning table is 4 bits per entry over 336 flip classes times 2187 twists, 367 KB, with 114 KB of move and conjugation tables beside it (the tables are not measured separately; Java: 68 MB, init 0.13 s).

### Shorter solutions: moves against probes and time

The first solution is not the shortest the search can find. `min_probes` (command line `--probes N`) and a minimum time (`--improve`) keep searching with a shrinking target, so every later solution is shorter than the one before. Measured on an Apple M2 Pro, 500 random cubes, move limit 21, tables prepared first, one run each (the machine carried a background load of about 2.5, so treat the times as approximate):

| Mode | Moves, mean | p90 | Time per cube, mean |
| --- | --- | --- | --- |
| default of the library, `--fast` (first solution) | 20.83 | 21 | 0.8 ms |
| `--probes 100` | 19.87 | 21 | 4.0 ms |
| `--probes 1000` | 19.16 | 20 | 42.1 ms |
| `--probes 10000` | 18.59 | 19 | 466.2 ms |
| `--improve -b 10` | 19.56 | 21 | 10.0 ms (1 cube of 500 had no solution yet) |
| `--improve -b 100` | 18.99 | 20 | 100.0 ms |
| `--improve -b 1000` | 18.48 | 19 | 1000.0 ms |
| `--improve --parallel -b 100` | 19.67 | 21 | 101.6 ms |
| `--improve --parallel -b 1000` | 19.27 | 21 | 1000.0 ms |

`--probes` counts work, so a row is repeatable on any machine; its time column is only what this machine took. `--improve` spends exactly its budget and returns the best solution found by then; spending the budget after a solution exists is not an error. The `--parallel` rows are worse than the serial `--improve` rows with the same budget: in these runs, searching the six orientations at once did not find shorter solutions, so prefer plain `--improve`. Why is not investigated. Moves fall by 0.7 and then 0.6 per tenfold increase in probes (100 to 1000 to 10000). The 4x4x4 hand-off already asks for 500 probes.

Commands (the example prints one line per run):

```sh
cargo run --release --example improve_curve -- 500 default
cargo run --release --example improve_curve -- 500 probes 1000
cargo run --release --example improve_curve -- 500 improve 100
cargo run --release --example improve_curve -- 500 parallel 100
```

The superflip needs about 1 to 3 s for its first (21 move) answer on this machine, so a time budget below that returns no solution at all, while `--probes` still returns one. No mode found the 20 move superflip solution.

Decided by the owner on 2026-10-24 and implemented: plain `cubacle solve` of a 3x3x3 now makes at least 3000 probes (random cubes 19.00 moves instead of 20.71, 135 to 184 ms in the table above, about 0.6 s at worst on a loaded machine). It is deterministic (the same output on every machine), bounded by probes and not by wall time, never longer than the first answer and cannot fail where the first answer succeeds. `--fast` restores the old output byte for byte. An explicit `--probes`, `--improve`, `--moves`, `--to`, `-m` or `-b` keeps its own meaning and turns the default off. The 2x2x2, the 4x4x4 and larger (their 3x3x3 stage keeps 500 probes), `solve --now`, the pattern shortcuts and the REST server are unchanged. `tests/cli_test.rs` pins the first answer with `--fast`.

```sh
cargo run --release --example default_modes -- random probes 1000
```

The set is `random`, `short` or `targets`; the mode is `default`, `probes N` or `improve MS`.

## Optimal solutions

`cubacle solve --optimal` ([guide](../cli.md#shortest-solutions)) finds a shortest solution in the half-turn metric and proves it. The module is `engines::optimal` (`OptimalSolver`); the default engine is injected through the `Solver` trait and supplies the first answer, the upper bound and the fallback. The design is clean-room: Korf's pattern databases, the inverse-cube lookup of optimal solvers and iterative deepening A* (IDA*), written from those ideas and from our own notes; no third-party solver source was read.

**Method.** The cube is kept as 12 edge bytes and 8 corner bytes (place and turn in one byte), once for the cube and once for its inverse; a move is a byte-table lookup per piece, written the same for any piece and read from the facelets rather than typed in. The lower bound is the largest of several pattern databases, each looked up for the cube and for its inverse (both are as far from solved). A database stores, for the positions and turns of a few pieces, the fewest moves that put them right with the other pieces ignored, 4 bits per state, built by a breadth first search over the 18 moves on up to four threads and kept in the cache directory like the 5x5x5 tables. The search starts at the lower bound and deepens by one move; it never tries a move on the face just turned, and of two opposite faces only one order. The first solution found at a depth is a shortest one. The depth stops below the default engine's length: a search that ends with nothing shorter has proved the default answer shortest.

| Tables | Databases | Size | States each | Mean value | Build CPU (Mac, loaded, 2 to 3 threads) |
| --- | --- | --- | --- | --- | --- |
| Small (`--max-memory` 90 and up) | all 8 corners; 6 edges (0 to 5); 6 edges (6 to 11) | 42.0 + 20.3 + 20.3 = 83 MiB (86 MB) | 88,179,840; 42,577,920 each | 8.76 (max 11); 7.62 (max 10) | 49 s in all |
| Large (`--max-memory` 555 and up, the default) | all 8 corners; 7 edges (0 to 6); 7 edges (5 to 11) | 42.0 + 243.6 + 243.6 = 529 MiB (555 MB) | 88,179,840; 510,935,040 each | 8.76 (max 11); 8.45 and 8.49 (max 11) | 328 s for the two 7-edge tables |

Both sets are inside the 1.5 GB cap (the large one uses a third of it). The corner database is shared by both sets. The mean bound at the start of a random cube is 9.0 with the small set and 9.2 with the large one, so the large set pays off in the nodes below the root, not at the top.

**Measured** on an Apple M2 Pro (16 GB) that carried a load average of 100 to 200 from other jobs throughout, so times are CPU seconds (user plus system) of a single search thread and still vary by about a third from run to run. Cubes come from a fixed-seed generator in `examples/optimal_measure.rs`: a random walk of 80 moves stands in for a random state, a walk of 16 moves gives cubes of 14 to 16+ moves, and "short" cubes are walks of 8 to 14 moves.

| Cubes | Tables | Proven within the budget | CPU s of the proven: mean / p95 / max | Mean bound at the start | Search speed |
| --- | --- | --- | --- | --- | --- |
| 30 short (8 to 14 moves; optimal mean 10.63) | Small | 30 of 30 (budget 60 s) | 0.08 / 0.23 / 1.41 | 8.07 | about 11 M nodes/s |
| 30 short | Large | 30 of 30 (budget 60 s) | 0.03 / 0.12 / 0.45 | 8.40 | about 8 M nodes/s |
| 15 walks of 16 moves | Large | 7 of 15 in 40 s, 5 of 15 in 10 s (optimal 14, 14, 14, 14, 15, 16, 16; the other 8 need more) | 11.4 / 37.4 / 37.4 | 9.07 | 9 M nodes/s |
| 30 random (80-move walks) | Large | 0 of 30 in 60 s, 0 of 30 in 10 s | none | 9.17 (Small: 9.00) | 5.3 M nodes/s (measured with the portable step, machine busiest) |

Two of the walk cubes that the 40 s budget left open were run to the end, with both table sets. Both have an optimal length of 16:

| Cube | Tables | Nodes | CPU s |
| --- | --- | --- | --- |
| walk 16 number 1 | Small | 1,511,798,503 | 134 |
| walk 16 number 1 | Large | 336,905,689 | 44 |
| walk 16 number 4 | Small | 4,309,635,161 | 341 |
| walk 16 number 4 | Large | 1,111,959,515 | 124 |

So the large set needs a quarter of the nodes (4.5 and 3.9 times fewer) and a third of the time (3.1 and 2.7 times less) of the small one, though each node is slower (the lookups miss the cache). The effort grows about fourfold to tenfold per extra move (optimal 14: about 10^7 nodes, 15: 3 x 10^7, 16: 3 x 10^8 to 10^9). Random cubes need 17 moves on average (18 for most of them); at this rate that is about 10^10 nodes, tens of minutes to some hours on one core, and 19 or 20 moves is days. This is an extrapolation from the rows above, not a measurement: none of the 30 random cubes finished in 60 s CPU, which is why the command takes a budget and says clearly when it did not prove anything. What the large hosts should measure is in the note "Large hosts measure the big tables, the Mac sets the default".

**Memory.** A `solve --optimal` with the large set had a peak resident size of 534 MiB (560,087,040 bytes, measured with `/usr/bin/time -l`, the default engine included); the build of a 244 MiB table keeps that table in memory next to the ones already loaded, so it stays well below the cap.

**Vector step.** The hot loop is the move step on the byte arrays. On aarch64 (NEON is baseline) the step is `vqtbl2q_u8` for the forward arrays and `vqtbl1q_u8` for the inverse ones, in the single `unsafe` module `engines/optimal/vector.rs`; other targets run the portable loop. A test compares the two on random cubes. Search of the same 8 cubes with exactly 110,543,661 nodes (the node count is fixed, so the work is identical), CPU seconds, three alternating runs each: portable 16.9, 16.9, 19.5; NEON 11.8, 10.4, 11.1, so NEON is 1.5 to 1.8 times faster overall. An x86 version (AVX2 `vpshufb`, chosen at run time with `is_x86_feature_detected!`) replaces `vector::turn(cube, tables, move)` only; the function takes and returns a `Cube` and is the whole interface.

Reproduce (the first run builds the tables):

```sh
cargo run --release --example optimal_measure -- --tables large --kind random --cubes 30 --budget 60
cargo run --release --example optimal_measure -- --tables large --kind short --cubes 30
cargo run --release --example optimal_measure -- --tables large --kind 16 --from 1 --cubes 2 --budget 900
cargo run --release --example optimal_measure -- --tables large --kind 16 --cubes 8 --nodes 20000000
```

## Comparison with the Java original

Reference: [cs0x7f/min2phase](https://github.com/cs0x7f/min2phase) (Java), checked out at commit 4d183b9. The Rust core comes from the MIT-licensed [min2phase_rust](https://github.com/cs0x7f/min2phase_rust) of the same author; provenance is recorded in `NOTICE.md`.

What was ported: the two-phase search, the coordinate and symmetry tables, the three-axis, inverse and pre-move tricks. What is new in cubacle: the typed `Solver` interface and replay check, the persistent worker pool, `solve_batch` and `solve_parallel`, the probe minimum as a counted option, and the golden-file test that pins the search output for 554 fixed cubes.

Claimed by the Java project (`Benchmark.md`, not measured by us, machine not stated): full initialization about 195 ms; 0.685 ms per cube for an unlimited search, 0.805 ms for 21 moves and 4.62 ms for 20 moves; memory about 1 MB per its table note; average length 19.29 with 500 probes taking 19.4 ms.

Measured by us (same 1000 cubes, same machine, warm JVM, one thread):

| | Java min2phase | cubacle |
| --- | --- | --- |
| Moves, mean / median / p90 / max | 20.52 / 21 / 21 / 21 | 20.81 / 21 / 21 / 21 |
| Time, mean / median / p90 | 0.567 / 0.349 / 1.165 ms (max 12.9) | 0.482 / 0.290 / 1.011 ms |
| Init | 0.13 s | 41 ms |
| Peak memory | 68 MB | 3.9 MB |
| Throughput, 12 solves in flight | | 6.5x Java single-thread [D] |

cubacle was 0.72x of Java on one thread while its core was an older min2phase variant without twist-flip pruning. It now has the upstream twist-flip pruning with conjugate pruning (a 4-bit table over flip classes and raw twists, and a second bound on the cube conjugated by a quarter turn about the U-D axis); the answers did not change (golden file and all fixtures pass untouched). Counted at the same place, cubacle searches 1,087 phase 1 nodes per cube against 4,710 before and 1,153 in Java, with 12.3 probes before the next change (7.4 in Java), and solves 1.75x faster than before. `MAX_DEPTH2` is now 12, as upstream (it was 13); that changes answers (golden file re-recorded, 225 of 554 rows) and on the 1000 cubes gives 1,159 nodes and 13.9 probes per cube, a mean of 20.67 moves (20.81 before) and 0.465 ms per solve (0.466 before) [M]. The Java claim above (0.685 ms) was measured on another machine and is not comparable with these figures.

## Limits and failure modes

- An impossible state (twisted corner, flipped edge, parity) or a facelet string that is not a cube is `InvalidInput`.
- A move limit the search cannot meet in the budget fails with `Exhausted`; a budget that ends first fails with `BudgetExhausted`.
- `solve_parallel` and time-budgeted searches are not guaranteed to return the same solution on every run; the result is always valid within the move limit.
- `solve_batch` ignores the time budget: every cube runs to completion.

## Targets with open stickers

`Solver::solve_to` has two routes for a `Target`. If the target fixes only whole edges and centers, at most five edges, a breadth-first search over just those pieces (12P5 * 2^5 states at the most) gives the exact distance, so the answer is proven shortest: the cross takes 0.03 s and 4.5 MB, a fifth edge 0.7 s and 25 MB. Any other target is enumerated into the complete cubes it allows; with at most 24, the two-phase search solves the way to each and the shortest is kept, reported as `best found` since two-phase is not optimal. More completions (a face, F2L) are refused with a message naming the supported forms. See [Targets with open stickers](../cli.md#targets-with-open-stickers).
