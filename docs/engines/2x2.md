# 2x2x2 engine

Part of [Engines and limits](_index.md). Numbers across all engines are on [Performance](../performance.md).

## What it solves and how

`PocketSolver` solves any 2x2x2 optimally in the half-turn metric: U, R and F turns by 90 or 180 degrees. A 2x2x2 has no centers, so one corner is kept fixed and the other seven corners give 7! x 3^6 = 3,674,160 states. The engine builds a breadth-first distance table of all of them (maximum depth 11, 4-bit entries), then walks down the table from the given cube to the solved one. The input is normalized by a whole-cube rotation to the fixed corner, and the resulting moves are mapped back, so the answer applies to the cube as given. A cube that is solved in any orientation needs no moves.

## Input and orientation contract

The cube is 24 facelets. Because there are no centers, color input needs a [color scheme](../cli.md#color-schemes). There is no final rotation: the solution turns the cube itself into a solved cube.

## Options

| Option | Effect |
| --- | --- |
| Move limit | Solutions are optimal, so a limit below the optimal length fails with `Exhausted`. CLI default 21 (never binding: the longest optimal solution has 11 moves). |
| Time budget | Checked during the search. It cannot interrupt the table build, and the build counts against the budget. |
| `min_probes` | Not used: there is one answer, the shortest. |
| Threads | Not used. One solve is one thread; many solves spread over cores with the server or your own threads. |

## Tables

One table of 1,837,080 bytes (3,674,160 states at 4 bits), built on first use or by `prepare()`, behind a `OnceLock`, shared by the whole process. There is no cache file. Measured build time (cold, one thread): 64 ms (95 ms on the first run of a process) [M]; `solve -v` on a cold process reports about 110 ms for the first solve, build included. Peak resident memory of a process that builds the table and solves: 18.7 MB [M].

## Performance

Measured on an Apple M2 Pro, 1000 random cubes, tables prepared first (method and marks on [Performance](../performance.md#method-and-marks)).

| | 1 thread | all cores (one solve) |
| --- | --- | --- |
| Moves, mean / median / p90 / max | 8.76 / 9 / 10 / 10 (optimal) | not applicable |
| Time per solve, mean / median / p90 | 0.002 / 0.002 / 0.003 ms | not applicable |
| Table build (cold) | 64 ms (95 ms first run) | not applicable |
| Peak memory | 18.7 MB | not applicable |

A solve takes about 2 microseconds with a ready table, so one core does hundreds of thousands per second; the thread question does not arise. (The earlier repository note recorded about 299 ns; the mean measured in the common method is 0.002 ms.)

## Comparison with the Java original

There is none. The 2x2x2 solver was written from scratch for cubacle: no code was copied from other solvers, and none of the `cs0x7f` repositories (min2phase, cube555, TPR-4x4x4-Solver) contains a 2x2x2 solver. There is therefore nothing to measure against and no claim to check. The exact distance table makes the result optimal by construction.

## Limits and failure modes

- A cube that is not a 2x2x2, or an impossible state, is `InvalidInput`.
- A time budget shorter than the table build on a cold process fails with `BudgetExhausted`; call `prepare()` first.
- A move limit below the optimum fails with `Exhausted`.

## Targets with open stickers

`Solver::solve_to` takes a `Target`, a map from every sticker to the colors allowed there. Every state is tested against the target (also after each of the 24 whole-cube rotations, as for complete targets); the states that meet it are the sources of a breadth-first search over the same move tables, which gives the exact distance to the nearest goal. The answer is proven shortest, and a target no state meets fails with `Exhausted` and a message that starts with `unreachable`. Measured: 0.25 to 0.3 s and about 30 MB for any mask tried, on top of the 0.08 s plain solve. See [Targets with open stickers](../cli.md#targets-with-open-stickers).

## Reproduce

```sh
cargo build --release
target/release/cubacle solve --size 2 --scramble "R U R' U'" -v
```

The output is `elapsed ..., probes -` on stderr and the solution `U R U' R'` on standard output. The elapsed time of the first solve includes the table build.
